      final _localNotifications = FlutterLocalNotificationsPlugin();

    **2. `initialize()` method** (idempotent, checks _initialized):
    - Create Android notification channels:
      - `high_importance_channel` (id: `'high_importance_channel'`, name: `'Important Notifications'`, description: `'For @mentions, DMs, and task notifications'`, importance: `Importance.max`) — per RESEARCH.md Pattern
      - `silent_channel` (id: `'silent_channel'`, name: `'Silent Notifications'`, description: `'For badge-only updates'`, importance: `Importance.min`) — per D-18 silent push
    - Initialize `flutter_local_notifications` with Android settings: `AndroidInitializationSettings('@mipmap/ic_launcher')`

      ```dart
      await _firebaseMessaging.requestPermission(
        alert: true, badge: true, sound: true,
      );
      ```
    - Get initial FCM token, store it: `await _saveToken(token)`
    - Subscribe to `onTokenRefresh` stream, call `_saveToken` on each refresh
    - Register `FirebaseMessaging.onMessage.listen(_handleForegroundMessage)`
    - Register `FirebaseMessaging.onMessageOpenedApp.listen(_handleNotificationTap)`
    - Check `FirebaseMessaging.instance.getInitialMessage()` on cold start — if non-null, call `_handleNotificationTap`

    **3. `_saveToken(String token)` method:**
    - Get current user from FirebaseAuth
    - If user is null, return early
    - Update Firestore `users/{uid}` with `FieldValue.arrayUnion([token])` on the `fcmTokens` field
    - Per RESEARCH: Use `arrayUnion` so multiple device tokens can accumulate

    **4. `_handleForegroundMessage(RemoteMessage message)` method:**
    - Parse `message.data` to determine notification type
    - Use `flutter_local_notifications` to show a local notification
    - Use the `high_importance_channel` for all messages (differentiated on the server side in the next plan)
    - Show notification with title from `message.notification?.title` (or fallback to 'Campus Link') and body from `message.notification?.body` (or fallback to 'New message')

    **5. `_handleNotificationTap(RemoteMessage message)` method:**
    - Parse `chatId` from `message.data['chatId']`
    - Parse `chatType` from `message.data['chatType']` (defaults to 'group')
    - Navigate to the correct screen:
      - For group chats: Navigate to `/chatScreen` (clear stack), then push a new GroupChatScreen with the correct ChatItem
      - Use `Navigator.pushNamedAndRemoveUntil(context, '/chatScreen', (route) => false)` to clear stack to ChatsScreen
    - If `chatId` or navigation context is unavailable, return silently

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| FCM -> Client | FCM messages arrive from external source (Google FCM servers). Data payload parsed in isolate. |
| Client -> Firestore | FCM token stored in users/{uid}/fcmTokens — token could theoretically leak user identity |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-04 | Spoofing | FCM onMessage handler | accept | FCM tokens are generated by Google Play Services, not user-controlled. Messages arrive from trusted FCM infrastructure. |
| T-07-05 | Tampering | _handleNotificationTap navigation | mitigate | Use `pushNamedAndRemoveUntil` with clear-stack pattern. Only parse chatId from trusted data payload (sent by our own Cloud Function). Do NOT accept arbitrary navigation routes. |
| T-07-06 | Information Disclosure | fcmTokens in Firestore | accept | Tokens are public identifiers (anyone with the token can send a message, but cannot derive user identity). Store in user doc which is already readable by authenticated users. |
</threat_model>
